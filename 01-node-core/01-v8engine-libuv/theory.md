## 1. V8 Engine & libuv: Архітектура Node.js

Node.js — це не мова програмування і не фреймворк, а **C++ програма (середовище виконання / Runtime)**, яка об'єднує двигун V8, бібліотеку libuv та набір C++ binding'ів для зв'язку JavaScript із системою.

```
+-------------------------------------------------------+
|                    Ваш JS Код                         |
+-------------------------------------------------------+
|               Node.js Core API (fs, http)             |
+-------------------------------------------------------+
|                 C++ Bindings / Node API               |
+-------------------+-----------------------------------+
|   V8 Engine       |          libuv                    |
| (JS Engine, JIT,  | (Event Loop, Thread Pool,         |
|  Memory, GC)      |  Async I/O, OS Abstraction)       |
+-------------------+-----------------------------------+

```

### V8 Engine (Двигун)

* **Завдання:** Компіляція та виконання JavaScript-коду.
* **Як працює:**
1. Парсить JS-код і будує **AST** (Abstract Syntax Tree).
2. Інтерпретатор **Ignition** перетворює AST у байт-код і починає його виконувати.
3. JIT-компілятор **Turbofan** відстежує "гарячі" (часто викликані) функції та компілює їх напряму в машинений код для максимальної швидкості.


* **Також V8 відповідає за:**
* Виділення пам'яті (Call Stack, Heap).
* Збір сміття (**Garbage Collection**).



### libuv (Мультиплатформенна C-бібліотека)

* **Завдання:** Забезпечення асинхронного, ненаблокуючого вводу/виводу (Non-blocking I/O) та кросплатформенності (Linux, macOS, Windows).
* **Компоненти:**
1. **Event Loop (Цикл подій):** Керує чергами подій та колбеків.
2. **Thread Pool (Пул потоків):** Обробляє важкі/синхронні операції, які неможливо зробити асинхронно на рівні ОС.
3. **Event Queue / I/O Polling:** Взаємодіє з системними викликами ОС (`epoll` в Linux, `kqueue` в macOS, `IOCP` в Windows).

## 2. Single-Threaded JS + Thread Pool для I/O

JavaScript у Node.js виконується в **одному головному потоці (Main Thread)**. Це означає, що ваш JS-код (Call Stack) обробляє завдання послідовно, одне за одним.

Однак сама платформа **Node.js НЕ є однопотоковою**.

### Як розподіляється робота:

1. **Non-blocking System I/O (Головний потік + ОС):**
мережеві запити (`http`, `https`, `net`, `sockets`). ОС сама вміє обробляти мережеві сокети асинхронно без залучення додаткових потоків CPU (через `epoll`/`kqueue`/`IOCP`). Node.js просто реєструє події в libuv і чекає на відповідь від ОС.
2. **Libuv Thread Pool (Допоміжні потоки C++):**
Використовується за замовчуванням для **4 потоків** (можна змінити через змінну оточення `UV_THREADPOOL_SIZE=N`, максимум 1024).
Сюди відправляються завдання двох типів:
* **I/O операції з файловою системою (`fs`):** ОС не має єдиного надійного асинхронного API для файлів на всіх платформах.
* **Важка криптографія:** `crypto.pbkdf2`, `crypto.randomBytes`, `crypto.scrypt` тощо.
* **Стиснення даних:** `zlib`.
* **DNS lookup:** `dns.lookup` (викликає синхронну системну функцію `getaddrinfo`).

## 3. Приклади та Демонстрація

### Приклад 1: Блокування головного потоку (CPU-bound)

Оскільки JS однопотоковий, важка математична обчислювальна задача блокує увесь сервер:

```javascript
import http from 'node:http';

const server = http.createServer((req, res) => {
  if (req.url === '/heavy') {
    // Блокуємо Call Stack на кілька секунд
    let count = 0;
    for (let i = 0; i < 5e9; i++) {
      count++;
    }
    return res.end(`Heavy task done: ${count}`);
  }

  if (req.url === '/fast') {
    return res.end('Fast response!');
  }
});

server.listen(3000, () => console.log('Server running on port 3000'));

```

*Якщо один користувач перейде на `/heavy`, будь-який інший користувач, який відкриє `/fast`, чекатиме, поки завершиться цикл `for`, бо Call Stack зайнятий.*

---

### Приклад 2: Демонстрація роботи Libuv Thread Pool

Перевіримо, як 4 за замовчуванням потоки libuv паралелять важкі криптографічні операції:

```javascript
import crypto from 'node:crypto';

const start = Date.now();

function runHash(id) {
  // pbkdf2 виконується в Thread Pool libuv
  crypto.pbkdf2('password', 'salt', 100000, 512, 'sha512', () => {
    console.log(`Hash ${id}:`, Date.now() - start, 'ms');
  });
}

// Запускаємо 5 важких операцій
runHash(1);
runHash(2);
runHash(3);
runHash(4);
runHash(5);

```

**Що відбудеться при запуску:**
Перші 4 хеші виконаються приблизно за однаковий час (наприклад, ~200ms), оскільки зайняли всі 4 потоки Thread Pool. 5-й хеш буде чекати, поки звільниться один із потоків, і завершиться через ~400ms.

> **Експеримент:** Якщо на початку файлу додати `process.env.UV_THREADPOOL_SIZE = 8;` (і запустити скрипт), усі 5 запусків виконаються паралельно за ~200ms.

## Питання: чому таймер із затримкою 0 виконується останнім в коді order.js? Що станеться, якщо всередині microtask постійно додавати нові microtask?

Коротка відповідь: **`setTimeout` створює Macrotask (макрозадачу), а Promises / `queueMicrotask` створюють Microtasks (мікрозадачі). Event Loop має чітке правило пріоритетів: мікрозадачі ВЗАГАЛІ НЕ ДАЮТЬ Event Loop перейти до наступної фази або макрозадачі, поки черга мікрозадач не стане повністю порожньою.**

### Крок за кроком, що відбувається при виконанні скрипту:

1. **`console.log('1: sync')`**
* Потрапляє в Call Stack (синхронний код) і одразу виконується.
* **Вивід:** `1: sync`

2. **`setTimeout(..., 0)`**
* Створює макрозадачу та реєструє таймер у фазі **Timers** у libuv.
* Навіть із затримкою `0`, код колбеку НЕ виконується негайно — він реєструється і чекає на відповідну фазу Event Loop.

3. **`Promise.resolve().then(...)`**
* Створює мікрозадачу і кладе її колбек у **Microtask Queue**.

4. **`queueMicrotask(...)`**
* Кладе ще один колбек у ту саму **Microtask Queue** (відразу після промісу).

5. **`console.log('2: sync end')`**
* Потрапляє в Call Stack і виконується.
* **Вивід:** `2: sync end`

6. **Очищення Microtask Queue (Критичний момент!):**
* Поточний модуль (main script) завершив свій синхронний виконання.
* Перш ніж Event Loop зможе зробити хоча б один крок далі (перейти до фази Timers), V8 **повістю вичерпує чергу мікрозадач (Microtask Queue)**:
* Виконується колбек промісу → **Вивід:** `3: promise (microtask)`
* Виконується `queueMicrotask` → **Вивід:** `3b: queueMicrotask`


7. **Перехід до Macrotask / Timers Phase:**
* Черга мікрозадач порожня. Тепер Event Loop переходить до фази **Timers** і виконує зареєстрований таймер.
* **Вивід:** `4: timer (macrotask)`

## 2. Що станеться, якщо всередині microtask постійно додавати нові microtask?

Якщо мікрозадача рекурсивно створює нові мікрозадачі, ви викличете **блокування Event Loop (Event Loop Starvation)** або **зависання/падіння викликів**.

### Приклад коду:

```javascript
function infiniteMicrotask() {
  Promise.resolve().then(() => {
    infiniteMicrotask();
  });
}

infiniteMicrotask();

setTimeout(() => {
  console.log('Цей таймер НІКОЛИ не виконається!');
}, 0);

```

### Що відбувається "під капотом":

1. Оскільки V8 зобов'язаний опустошити **всю** чергу Microtask Queue перед тим, як повернути контроль Event Loop, процесор потрапить у безкінечний цикл очищення цієї черги.
2. **Таймери, I/O операції (читання файлів, мережеві запити) та будь-які інші макрозадачі БУДУТЬ ЗАБЛОКОВАНІ НАВІЧНО.**
3. На відміну від безкінечного рекурсивного синхронного виклику (який викликає помилку `Maximum call stack size exceeded`), нескінченні мікрозадачі НЕ заповнюють Call Stack одночасно (кожна мікрозадача завершує свій стек перед викликом наступної), тому вони просто **100% завантажать один потік CPU** і застосунок повисне без помилки "stack overflow".

## Важливий нюанс: `process.nextTick` vs `Promise`

У Node.js є дві черги мікрозадач:

1. **`process.nextTick` Queue** (має ВИНЯТКОВИЙ найвищий пріоритет, виконується раніше за звичайні Promises).
2. **Promise / Microtask Queue**.

Якщо ви викликаєте `process.nextTick` всередині `process.nextTick`, ви так само заблокуєте Event Loop, навіть для звичайних `Promise.then()`.
